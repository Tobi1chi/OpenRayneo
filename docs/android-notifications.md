# 高德 App 通知导航与显示对齐

2026-10-12，用户要求以高德 App 作为导航主体，OpenRayneo 读取导航通知并显示到眼镜。0.2.1-dev 取代此前的 SDK 导航路径，无需 OpenRayneo 的高德 Key、地图 SDK 或定位权限。

## 真实通知证据

通过 Android `cmd notification list` 找到高德通知 key，再逐条 `get`；未读取其他 App 的通知正文。小米 13 上实际存在以下通知：

| 来源 | 字段内容 | 用途 |
| --- | --- | --- |
| `com.autonavi.minimap`，`ROUTE_CHANNEL_ID`，id `1236` | `android.title` 为路名；`android.text` 为 `直行314米｜高德导航中` | 含明确动作和距离，可转换为网格 |
| 同 App、同频道，id `99910003`，category `navigation` | 标题为持续导航提示；正文为 `正在为您骑行导航>>` | 只有运行状态，不能推断方向和距离 |
| 系统自动分组汇总 | 无有效文本 | 忽略 |

HyperOS 的 `miui.focus.param` 还含相同的 `title`、`content` 展示字符串。读取标准通知文本及这两个展示字段，不执行其中的动作或链接，不做图标识别、界面抓取或无障碍操作。

真实通知已证明当前版本能提供直行动作与距离。转弯格式兼容逻辑另有合成测试，但不能把合成测试当成所有路况和所有高德版本的实测。

## 接收与解析

用户在系统界面授予通知使用权；`NavigationNotifications` 只处理高德的已观察导航频道或 navigation 类别，忽略其他 App 和分组摘要。通知内容仅保留于本机内存，不写入正常日志或发送给模型。手机页面列出候选内容供用户核对。

首次发现频道中含明确动作／距离的通知时自动跟随；手动选择可覆盖它。0.4.0 起持久化关闭自动选择：手动停止后，即使还从未选择过通知，也不会被随后到达的首条通知重新启用。选择保留为本地通知 key，更新同一条通知时替换画面。通知被移除、服务断开或新的文本无法识别时清除旧方向，显示简短状态；不保留过期箭头作为有效指令。

当前解析支持“直行314米”这类动作在前的格式，以及“80米后右转”“前方1.2公里后左转”这类明确指令。路名、品牌后缀和剩余总里程不作为转向距离。当前网格距离范围沿用 Mac 的 0–9999 米；超出范围或无法识别时提示查看手机，不截断为错误数值。

## 0.2.1–0.2.2 导航显示基线

当时导航与 Mac 一样使用字幕通道 `0x13`，不是通知弹窗，也不是实时提示页：

1. type `7` 请求字体 `2`、宽度 `100`、行数 `5`。
2. 等待匹配 SID 的 type `8`、`code:1`，核对 `effective_config` 三项都一致；不一致就停止，等待用户重新打开显示。
3. 等待 500 ms，再发送首个 type `5`、mode `3`、status `1` 的完整网格。
4. 基础网格为 20×5；首帧无前缀，后续更新按 Mac 已验证规则只在整段开头补一个 `U+3000`。同样的画面不重复发送。
5. 0.2.2-dev 在右侧底行加入所选通知标题中的路名（第 13–20 列，共 8 格），保留标题原文如“沿…路”。超长内容静态截取，不增加行数；完整名称仍在手机上。大箭头、距离和动作的位置不变。未识别、等待、断开等状态也使用固定五行。重开或切换页面后重新计算首帧。

0.2.0-dev 用户报告自动滚动。已修复未核对实际布局、缺少首帧等待、长文本直接写入以及重复写入路径。2026-10-12，用户在 0.2.1-dev 通知导航测试中明确确认“显示正常，不再滚动”。后续增加信息时保留该固定布局基线。

## Agent 问答

手机 Agent 和电脑 Codex 的眼镜回答改用实时提示通道 `0x17`：type `1` 启动、type `2` 回执，type `5`、mode `4` 更新 `source_transcript`（问题）和 `target_translation`（回答）。停止发送 type `3`、reason `2`；0.2.1–0.2.2 导航停止则用字幕通道及 reason `10`。

取消前 100 字截取。传输仍受协议帧长度上限约束，过大的内容会报告发送失败，不静默裁成另一份答案。0.2.1–0.2.2 提示页固有音频上行直接丢弃，不解码、保存或上传；当时“结束眼镜回答”关闭页面。导航跟随中显示回答 12 秒后恢复导航。

## 0.3.0 默认实时提示与双声道

用户明确选择导航也改为实时提示页，以持续收音为优先，重新验证导航布局。连接成功后默认启动 `0x17`；默认提示、导航与问答在同一 SID 中更新文字，选通知、通知变化、结束回答及 12 秒恢复导航均不发送 stop/start。明确暂停、恢复、断开或设备结束才终止旧会话。收到启动确认后开始处理匹配 SID 的 type 4 音频；旧会话、其他协议和确认前的音频不进入解码器。

导航不再发送 20×5 大块箭头：`source_transcript` 为方向符号／距离／动作（如 `↑ 314米 直行`），`target_translation` 为所选通知标题，换行与制表符转空格并限制 12 字。无法识别或通知移除时显示短状态，不残留旧指令。实时提示页不沿用字幕页的有效布局确认或首字符补偿；保留确认后的 500 ms 等待。新页面的字号、换行和是否滚动需用户重新目视验收，不能套用 0.2.1 的通过结果。

`PromptAudio` 用手机系统 MediaCodec 解码器处理单包 Opus，48 kHz／双声道／PCM16，按交错样本拆分两路缓冲供后续消费者接入。当前只计算并显示两个音量，不录音、不上传、不识别。检查 Opus TOC 声道标志，单声道包提示等待，不复制为假双路。队列最多 16 包，过载丢弃；UI 每秒更新，超过 3 秒无有效 PCM 显示等待。开始／停止切换以会话代数隔离旧任务，旧解码结果不能重置已暂停状态。

验证：构建与 Lint 通过；临时会话测试验证 20 次导航／问答更新保持一个 SID 和一次启动、音频持续分发、停止及旧 SID 隔离、错误协议与确认前音频过滤、短路名及过期导航清除。小米 13 真机系统解码测试将不同频率的合成音分别编码进两个 Opus 声道：90 包全部解码为 86,400 个双声道采样帧（1.8 秒），无丢弃或解码错误，两路频率保持分离；单声道拒绝及快速启停隔离通过。该测试未使用眼镜采音，不代替真实蓝牙音频与佩戴显示验收。

## 0.3.1 固定导航与字幕音频

用户反馈 0.3.0 页面仍在、文字几秒后消失、两个音量持续变化，随后要求恢复原导航并保留音频，允许单声道。ASR 接入另行暂停。未交付此前拟议的实时提示周期补发方案。

官方 APK 重新按原类名提取的 `E3.V.i` 确认：`AI_SUBTITLE` (`0x13`) 的 type 4 二进制字段为音频，JSON 包含 SID／seq，并进入翻译音频与共享 CAPTION 路由；`TELEPROMPTER` (`0x14`) 的 type 9 也有独立音频入口。固件字符串含字幕 START_REQUEST／START_REPLY、TranslateAudioAdapter 打开录音器、默认设置 `translation`／`ahead`。不能把既有 type 7 设置预览等同于字幕收音会话。

实现先在 `0x13` 发 type 1，settings.mode=`translation`，等待匹配 SID 的 type 2、code=1，然后在同一 SID 发 type 7 恢复原布局，核对 type 8 的 2／100／5 配置并等待 500 ms，再发 mode 3／status 1 完整网格。首帧不加补偿，后续整帧前补一个 U+3000；相同导航内容不重复写屏。type 2 确认后，匹配 SID 的 type 4 音频在布局协商和导航更新期间继续交给解码器；导航输出按 48 kHz 单声道处理，第二路缓冲为空。暂停、断连、配置拒绝、SID 切换会结束旧音频。界面明确区分无音频、等待音频和已解码，不以启动回执代替收到音频。

构建与 Lint 通过。临时测试覆盖启动／布局两阶段回执、首帧等待、原网格与更新补偿、显示去重不影响收音、SID 隔离、停止及错误布局拒绝。小米 13 系统解码器另通过 60 包单声道 Opus 检查，产生 57,600 个单声道采样（1.2 秒），无丢弃或错误，停止后状态清除；单声道不生成虚假的第二路缓冲。临时测试源码已移入废纸篓。新组合路径的实际音频到达、布局保持及持续显示仍待眼镜验收。

## 0.3.2 接收 BLE 业务数据

0.3.1-dev 用户确认导航等显示正常，音频提示为“等待眼镜音频”，并非解码异常。手机日志证实 type 2 与 type 8 先后确认；尚无真实字幕音频解码成功的证据。

检查发现 Android `RayneoConnection` 在完整模式下只处理 BLE 配对帧，其他 BLE 业务帧仅在 BLE-only 诊断模式下分发，同时也只在 BLE-only 模式下响应请求确认的帧。0.3.2-dev 去掉这两个模式限制，BLE 与 SPP 业务消息均送入现有接收器；保持导航布局与启动协议不变。仅在匹配已确认 SID 时接收音频，以最近 64 个业务 seq 消除双传输路径重复帧；无 seq 时不猜测重复。记录首个音频包的来源、字节数，以及首次会话不匹配，不记录原始音频或识别内容。

构建、Lint 和临时检查通过：BLE 音频、跨传输路径重复、确认前／旧 SID／停止后的音频拒绝、有限序号窗口及重连后序号复用。临时源码已移入废纸篓。此次修复了确实存在的 BLE 过滤问题，但它是否为本次等待音频的原因，需要更新后的真实接收日志验证。

## 0.3.3 停止导航不再进入默认实时提示

用户明确复现步骤为“进入导航 → 停止眼镜跟随 → 自动进入实时提示”。实际代码路径是 `NavigationFeed.stop()` 通知观察者，观察者调用 `showNavigation()`，由于导航已禁用，进入默认实时提示分支。此前将问题归为手动提词器抢占仅是初步假设，本次未据此新增提词器事件处理。

停止导航现在先暂停显示、取消回答恢复定时器、结束显示与音频，再通知导航观察者，避免观察者或随后通知重新打开默认页；蓝牙连接保留。暂停时自动模型回答也不打开页面。手动选择有效导航通知、恢复显示或主动“重新显示回答到眼镜”可重新取得显示控制。构建及 Lint 验证；真实按钮行为待安装后确认。0.3.2 的 BLE 音频修复仍保留，真实字幕音频接收尚待用户测试。

## 0.4.0 协调器重构

已实现 [眼镜协调器](android-state-machine.md)，取代 0.3.3 的全局暂停修补。导航停止、全局暂停、结束回答分别使用独立事件。停止导航不再打开默认实时提示，也不结束无关的当前回答；停止后发起的新任务仍可显示。回答恢复计时从内容写出后开始，眼镜退出、提词器活动、用户后续切换会使旧任务／计时器失效。

页面切换等旧停止命令写完，再按最新意图启动；关闭超时不盲目打开新页。意外重连保留空闲和已让出状态，BLE-only 不启动页面。导航布局、真实通知解析与 BLE/SPP 音频接收保留原路径；音频增加等待首包、已收包待 PCM、正常、断流和失败状态，可独立重启本地解码器。

本地构建、Lint、26 项协调器测试和 13 项协议联测通过；临时测试源码随后移除。0.4.0 真机切换行为及真实字幕音频仍待安装验证，不能沿用旧版导航显示确认作为此次重构的验收。

## 0.5.2 通知监听恢复

2026-10-17 用户报告通知授权正常，但偶发无法读取，重新开关权限后恢复。ADB 实际检查：小米 13 安装的是 0.3.2-dev，通知监听组件仍在授权列表中，应用最初处于 `stopped=true`，无进程、无监听服务；打开应用后旧版 BridgeService 启动，但仍未看到 NavigationNotifications 绑定。检查时高德没有活动导航通知，不能将这次静态观察当成已复现历史导航中断。

确认的代码缺口：`onListenerDisconnected` 只清空数据，不在后台请求恢复；回到前台仅当本地 `connected=false` 时请求 rebind；手动刷新也仅请求 rebind，不重新读取活动通知。启动先设置 connected 再逐条读取，快照没有整体替换／清除失效通知，生命周期回调也不区分旧实例。

修复：

- `NotificationRecovery` 单独管理通知监听连接，与眼镜显示状态机分离。已授权、连接中、已连接、断开和失败分别呈现。
- 断开后自动恢复，重连请求最多 3 次，每次等待 8 秒，失败间隔为 2／5 秒。耗尽后停止自动重试，前台再次进入或用户主动恢复可开启下一轮。
- 回到应用前台时，有活动监听实例就补读快照；导航跟随启用、BridgeService 运行时每 30 秒补读一次。授权状态不会代替监听连接状态。
- 用户“恢复通知读取”先解绑本应用监听，再请求绑定，不改变系统授权。有实例时使用 `requestUnbind()`；无实例时 Android 14+ 使用公开的 `requestUnbind(ComponentName)`。Android 13 没有这个按组件解绑接口，无实例时只尝试重新绑定。
- 连接后重新读取当前通知，只解析高德导航候选，一次替换候选集与就绪状态，清除快照中已消失的通知。保留选定 key 和跟随偏好，用户已停止的导航不会因此重新启用。
- 旧实例的断开／销毁回调不能清除新实例的数据。解绑后不依赖再次收到 disconnected 回调才启动恢复。
- 解析异常按单条隔离，日志仅记录异常类型、候选数与可解析数，不记录通知正文。设置和诊断显示授权、监听连接、候选数量与最近快照同步时间。

验证：构建、Lint 和 16 项临时测试通过，覆盖有授权但未连接、前台补读、手动解绑／重绑、无实例组件恢复、后台断开、旧实例销毁、重复恢复合并、重试次数上限、权限撤销、空快照、快照异常、同步绑定异常、持续读取失败、快照原子替换及保留明确停止／选择。临时测试源码在本阶段结束后清理。APK 已传入小米 13 下载目录，安装后的真实高德通知恢复待验证。

边界：进程被强行停止时应用代码无法运行重连，需要用户重新打开 App；不能承诺绕过系统停用或省电限制。Android 的公开 `getActiveNotifications()` 在部分版本会将内部 IPC 失败转为空数组；因此没有通知不被直接判定为权限失效，也不会因空列表反复解绑。它也不能修复高德本身未发通知或通知格式不含转向的情况。

### 小米真机根因与恢复证据（2026-10-17）

更新 0.5.2 后，手机前台进程正常，眼镜 BLE/RFCOMM 与提示页音频正常，但普通通知重绑连续超时。系统日志在 23:35:55 两次明确记录 `AutoStartManagerService: MIUILOG- Reject service`，目标为本应用 `.NavigationNotifications`，紧接 `NotificationListeners: AutStart Unable to bind notification listener service`。AppOps 同时显示普通 `RUN_ANY_IN_BACKGROUND: allow`、`START_FOREGROUND: allow`，小米 `MIUIOP(10008): ignore` 且有对应拒绝时间。通知授权存在，不代表小米允许后台启动这个服务。
